- ~~★★ **Expert mode attaches fewer knowledge cards than Strategy**~~ — **fixed 2026-08-18, on-Deck verification owed (KB-EXPERT-01).** Two mode-keyed knobs disagreed about what Expert means. `_budget_for_mode` gave Expert the **largest** card budget (speed 1 / strategy 3 / expert 5), while `implicit_route = (ask_mode or "").strip().lower() != "strategy"` put it on the **strictest** relevance bar — `IMPLICIT_ROUTE_RELEVANCE_FLOOR` 4.0 against `BM25_RELEVANCE_FLOOR` 1.0 — because the test asked for Strategy **by name** rather than for the thing Strategy stands for. So the mode a stuck player picks for maximum depth was the one hiding the most corpus. Measured on device 2026-08-17 (corpus `2026.08.16`, DRG Survivor `2321470`) and reproduced exactly on the seed corpus: *"what class should i pick"* → Strategy 2 cards, Expert 1 (`Upgrades and overclocks` scores bm25 2.13 and died at the 4.0 floor); *"what should i upgrade"* → Strategy 3, Expert 1. **Fix:** `_DECLARED_GAME_ASK_MODES = frozenset({"strategy", "expert"})` is now the single definition of "the user declared this Ask to be about the game", and the flag is membership in it. After: Expert 2 and 3 respectively, matching Strategy. **The coupling is the point.** The vector recall pass shipped the same day gates on the same flag, so Expert gained the loose floor *and* its own recall path in one edit — before this, Expert would have been the only declared-game mode with neither. `_budget_for_mode` now carries a docstring pointing at its sibling knob, from the side that drifted. **What is deliberately unchanged:** Speed stays implicit, and the other `ask_mode == "strategy"` tests elsewhere in the backend (roleplay suffix, compose intent, domain guidance) were left alone — they are different questions and widening them needs its own evidence. **Why no gate caught it:** KB-ASKMODE-01 asserted D17's promise that cards attach in *every* mode, which passed; nothing compared the counts *between* modes, and the two unit tests that touch mode use compat (where the floor is not route-keyed) or Speed. - ~~★★★ **Hybrid retrieval's vector half adds no recall — it only re-orders what BM25 already found**~~ — **fixed 2026-08-18, on-Deck verification owed (KB-RECALL-01).** Every candidate came from one FTS query and the vectors were then loaded **for those candidates only** — `_load_section_vectors(conn, [c.section_id for c in cards])` — so RRF re-ranked a keyword shortlist rather than fusing two recall paths. The guard was `if nomic_ready and cards:`, which meant that when BM25 returned nothing, **no embedding was computed at all** and a semantically perfect card was unreachable. Measured on Deck 2026-08-17 (corpus `2026.08.16`, floor 0.0, shortlist 30, so neither was the limiter): *"how do i kill the big armoured bug boss"* → 0 candidates with the Glyphid Dreadnought card present; *"which character is best for a beginner"* → 0 with Classes present; *"tips for the thorny plant level"* → 1, and the wrong card. **Fix:** `_vector_recall_sections` ranks **every** section of the resolved game by cosine and returns the above-floor cards the keyword half missed, plus the game's vectors; `_fuse_cards_by_rrf` takes them as `recall_cards` and fuses two genuine lists. A recall-only card takes an FTS rank one past the end of the keyword list — the same one-step backfill a vectorless card already took in the vector ranking, so the two halves stay symmetric and the top keyword hit is not unseated by a card FTS never found. Scoped per-game for the same reason `_search_sections` is (wrong-game advice is worse than none); brute force over 5–13 cards, so no ANN index — Phase 7's sqlite-vss item is now an optimisation of a path that exists rather than a prerequisite for it, and this is the **meaning-fallback** blend Phase 7 locked on 2026-07-30. **Gated to the explicit route.** The pass costs an embed round trip (793–900 ms on Deck) and, at a floor loose enough to catch a paraphrase, will attach *something* to almost any question — so it runs only when the user declared the Ask to be about the game, keyed off the same `implicit_route` flag that already picks the relevance floor, so the two cannot drift. (Consequence worth knowing: Expert is on the implicit route today, so it gets no recall pass until the open Expert-floor bug lands, which fixes both at once.) **The floor is measured, and the measurement is the interesting part:** across 15 paraphrased questions with a known answer and 12 off-topic Asks, the correct card scored **0.519–0.738** and the best card for an off-topic Ask scored **0.435–0.593** — the distributions **overlap**, so no absolute floor separates them. A z-score-over-the-game's-cards alternative was measured and rejected (off-topic z(top) ran 1.10–2.32 against 1.10–2.42 for relevant — with 5–13 cards in a game, *something* always stands out). The conclusion: whether an Ask is about the game is a **routing** question, not a retrieval one, which is why precision here rests on the route gate and `VECTOR_RECALL_FLOOR = 0.50` only has to beat `_genre_fallback` — the generic genre card that is what the explicit route attached before when BM25 found nothing (*"what is the capital of peru"* with DRG running still attaches "Soulslike basics: learn dodge timing…", which is the bar). `VECTOR_RECALL_K = 3` bounds what a wrong recall costs. **Result** on `kb_eval_v2` (98 labeled strategy rows, paired, one embedding per case): top-3 **95.9% → 100.0%**, top-1 unchanged at 83.7%, **zero** regressions. **Why no gate caught the original:** KB-RRF-01 confirmed the embed fires and the timings are non-zero; KB-EVAL-02 measured arm accuracy on queries that mostly had keyword hits. Neither asked whether the vector half ever changed *which* cards were found — the RRF unit tests all pass a shortlist in and are structurally unable to notice that nothing else could get in. Files: [knowledge_base_service.py](../../py_modules/backend/services/knowledge_base_service.py) (`_vector_recall_sections`, `_section_row_to_card`, `_fuse_cards_by_rrf`, `VECTOR_RECALL_FLOOR`, `VECTOR_RECALL_K`), 8 tests in [test_knowledge_base_service.py](../../tests/test_knowledge_base_service.py). Measurement: [rag-vector-recall-floor-2026-08-18.md](../audit/rag-vector-recall-floor-2026-08-18.md).

Fixed by moving the handlers onto the enclosing row `Focusable`s, with a `focusedStop()` lookup so one row handler still serves both columns. **(2) `focusRegisteredReplyStop` stamped `tabindex="-1"` on everything it touched** — the `<button>` and its `.Panel.Focusable` row — which removes those nodes from Steam's navigation graph. - ~~★★★ **Spoiler "tap to reveal" cannot be focused with a D-pad**~~ — **root-caused and fixed 2026-08-04 (third attempt), **confirmed on-Deck**.** The first two attempts failed because the model was wrong, and the correct one is bigger than this bug: **Decky runs plugin JS in SteamOS's `SharedJSContext`, whose `document` is a 14-element shell, while the QAM UI is rendered into a separate popup document.** Inside plugin code the global `document` therefore describes a page containing none of our markup. **Fixed 2026-08-03 — voice input was completely broken for two and a half weeks.**
`VoiceTranscriptionSession.status()` did not exist. `742db60` (*Voice STT session daemon*,
2026-07-17) replaced the `def status(self)` **signature line** with the new `_transcribe_pcm`
method and never re-added it, leaving `status()`'s two body lines stranded as **unreachable
code** after `_transcribe_pcm`'s `return`. Python does not warn about that, and neither did any
gate.

One deleted line broke four callers: `start()` and `stop()` inside the class, plus
`start_voice_transcription` and `get_voice_transcription_status` in `main.py`. Every voice
attempt raised `AttributeError: 'VoiceTranscriptionSession' object has no attribute 'status'`.

**Why the symptoms looked contradictory.** Settings correctly reported *voice ready* because
`get_voice_engine_status` checks the binary and model on disk and never touches `status()`; only
the Main-tab start path did. The engine was genuinely fine throughout — verified after the fact:
`binary_ready: true, model_ready: true, ready: true`. The **Voice input unavailable** message
that appeared later was the frontend reacting to repeated RPC failures, not a real missing
engine, so no reinstall was ever needed.

**Found from a user report, not a gate** — the traceback was only in `journalctl -u
plugin_loader`, since the exception was raised before the plugin's own logger ran. Worth
remembering: **plugin-side RPC exceptions land in the loader journal, not
`homebrew/logs/bonsAI/`.**

Coverage, both mutation-checked: `tests/test_voice_session_status.py` (5 tests, including a
public-surface assertion over `start`/`stop`/`force_stop`/`status`) and
`tests/test_no_unreachable_code.py` — an AST guard over `main.py` and all of `py_modules/` that
fails on any statement following a `return`/`raise`/`break`/`continue`. That second one is the
real mechanism: it catches the *fingerprint of a half-finished deletion* rather than this one
instance. It found zero other sites, so the tree is clean. Re-verified on the deployed plugin:
`status()` returns the state mapping. **On-Deck retry of a live recording is still needed.**
